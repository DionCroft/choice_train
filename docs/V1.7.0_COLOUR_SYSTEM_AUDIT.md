# V1.7.0-alpha Colour System Audit

**Status:** Technical implementation complete; school and physical-device validation pending
**Audit date:** 6 November 2026  
**Branch:** `feature/v1.7.0-alpha-ui-ux`  
**Promotion status:** audit completed and candidate promoted as stable `V1.7.0` on 7 November 2026

## Purpose

This audit responds to visual review that showed V1.7.0-alpha did not yet behave as one colour system. The teacher shell, selected learner theme, inherited learner components, JavaScript effects, and analytics canvases used overlapping but different palettes.

The goal is consistency and predictable meaning, not one mandatory colour scheme for every SEND learner. Theme, contrast, motion, sound, and presentation choices must remain configurable and tested with individual learners and practitioners.

## Evidence Reviewed

- desktop teacher/learner screenshots at a 3840 by 2160 browser viewport
- the embedded V1.6 stylesheet in `choice_train_V1.7.0-alpha.html`
- the V1.7 presentation layer in `choice_train_V1.7.0-alpha.css`
- `THEME_META`, task colours, interaction effects, heatmaps, and chart drawing in `choice_train_V1.7.0-alpha.js`
- the stable and alpha browser suites
- WCAG 2.2 contrast, non-text contrast, focus appearance, and use-of-colour requirements

## Baseline Findings

The findings below describe the pre-migration alpha captured at the start of the audit. They are retained to explain why the semantic system was introduced; the resolution is recorded after them.

### 1. Split ownership

The external alpha stylesheet owns the staff shell and selected layout refinements, while the embedded legacy stylesheet still owns most learner components. `applyTheme()` changes the legacy variables but fixed alpha and legacy literals continue to override them.

Consequence: selecting Calm Light produces a light stage beside dark navy cards, a grey progress track, cyan highlights, teal teacher actions, and a navy footer.

### 2. Too many literal colours

The source audit found:

- 199 colour-like literals in the versioned HTML across approximately 125 spellings
- 77 literals in the alpha stylesheet across 45 spellings
- 172 literals in JavaScript across 144 spellings, including legitimate theme palette definitions

The exact counts include gradients, alpha variants, and a small number of HTML entity false positives. The important finding is that component styling is not consistently derived from semantic tokens.

### 3. Theme coverage gaps

The selected learner theme does not fully control:

- progress track and station states
- prompt container and task-rule chip
- large cue card and choice cards
- image wells
- learner footer and status badges
- support highlight and ripple effects
- reward surfaces
- heatmap and mini-chart backgrounds/lines
- modal scrims and raised panels

### 4. Meaning changes between views

Teal means primary action in the teacher view, cyan means focus/current state in the learner view, blue means admin navigation, amber means both alpha status and warning, and navy is used both as neutral chrome and high-emphasis content.

The colours are individually readable in many locations, but the repeated changes weaken hierarchy and make state meaning less predictable.

### 5. Light-theme inconsistency

Calm Light and Light Classroom still use forced dark footer surfaces and legacy dark cue cards. Plain White uses a large selector-specific override block rather than the same semantic contract as other themes.

### 6. Programmatic colours bypass themes

JavaScript directly applies cyan cue rings, cyan/green ripples, dark canvas backgrounds, fixed green/amber/red heatmap points, and fixed chart lines. These do not adapt to theme selection or high-contrast needs.

### 7. Colour is sometimes the strongest state signal

Correct, incorrect, current, completed, selected, and warning states usually include text, shape, position, or border changes, but this is not enforced as a system rule. Future components could accidentally rely on hue alone.

## Target Semantic Contract

Every theme must provide the following roles:

| Token | Purpose |
| --- | --- |
| `canvas` | Outer learner background |
| `surface` | Standard content surface |
| `surface-subtle` | Grouping and secondary surface |
| `surface-raised` | Cards, prompts, modals |
| `text` | Primary text |
| `text-muted` | Secondary text that still meets contrast |
| `border` | Ordinary component boundary |
| `border-strong` | Selected, current, or structural boundary |
| `control` | Neutral control background |
| `control-hover` | Neutral hover/pressed background |
| `primary` | Main action and current-progress state |
| `primary-hover` | Main action hover/pressed state |
| `primary-soft` | Low-emphasis selected or informational surface |
| `on-primary` | Text/icon colour on primary |
| `success` / `success-soft` | Correct/completed outcome |
| `warning` / `warning-soft` | Caution, wait, or alpha status |
| `danger` / `danger-soft` | Incorrect, destructive, or failed state |
| `reward` / `reward-soft` | Progress celebration without implying correctness |
| `inverse` / `on-inverse` | Deliberate high-emphasis inverse surface |
| `focus` | Keyboard focus and explicit visual cue |
| `scrim` | Modal overlay |
| `shadow` | Theme-appropriate elevation |

Legacy variables such as `--panel`, `--accent`, and `--good` remain temporary aliases during migration. New or edited components must use semantic roles.

## Product Colour Rules

1. One semantic role has the same meaning in teacher, learner, and admin workspaces.
2. The staff shell uses the ChoiceTrain product palette; the learner stage uses the selected learner theme.
3. Selected learner themes must control every learner surface, state, effect, reward, and chart.
4. A state must not rely on colour alone. Use text, icon, border weight, position, or shape as a second cue.
5. Body text targets at least 4.5:1 contrast; large text targets at least 3:1.
6. Controls, focus indicators, selected boundaries, chart marks, and meaningful non-text elements target at least 3:1 against adjacent colours.
7. Muted text is still functional text and must meet 4.5:1 where it communicates instructions or state.
8. Focus uses one dedicated token and remains visibly different from selection.
9. Reward colour does not replace success colour, and warning colour does not imply error.
10. High Contrast remains a distinct theme; other themes are not described as clinically calming or universally SEND-friendly.

## Migration Plan

### Progress at 6 November 2026

- Milestone 1 complete: all learner themes implement and validate the semantic contract.
- Milestone 2 complete: learner stage, task, progress, feedback, reward, and footer surfaces now follow theme tokens without theme-specific patches.
- Milestone 3 complete: CPAT symbols, pointer trails, target cues, ripples, heatmaps, and chart drawing now resolve semantic colours at runtime; browser coverage verifies live theme switching.
- Milestone 4 complete: the teacher/admin shell now uses product semantic roles for controls, fields, navigation, status, analytics, overlays, disabled states, and focus; a regression guard rejects component-level colour literals.
- Milestone 5 complete for local technical validation: responsive state coverage, documentation, the full regression matrix, and repeatable visual evidence are in place. School observation and physical-device validation remain promotion gates.

### Milestone 1: Contract and tooling

- define semantic theme roles and compatibility aliases
- add a browser-accessible theme snapshot for test inspection
- add contrast and token-completeness tests for every theme
- add screenshot states for teacher, welcome, active task, reward, results, and admin

### Milestone 2: Learner surfaces

- migrate stage, progress, prompt, cue/choice cards, media wells, footer, badges, regulation controls, blank screen, and modal surfaces
- remove forced dark Calm Light and Light Classroom exceptions

### Milestone 3: States and effects

- migrate focus, selected, current, done, correct, incorrect, wait, no-go, cue, ripple, reward, and disabled states
- ensure each state has a non-colour cue
- make JavaScript effects read the current semantic palette

### Milestone 4: Admin and analytics

- migrate staff shell literals to product semantic tokens
- make heatmaps, charts, tables, and export cards coherent and readable
- test empty, populated, selected, error, and disabled states

### Milestone 5: Validation and documentation

- run stable and alpha regression suites
- capture desktop, tablet, and mobile visual evidence across all themes
- update architecture, user guide, design decisions, school audit, tests, and changelog
- stamp and push reviewable commits without changing `index.html`

## Implemented Outcome

- All eight alpha learner themes provide the complete semantic role set and pass automated text/non-text contrast pairs used by the interface.
- Learner components no longer need Calm Light, Light Classroom, or Plain White selector patches; themes own the task, feedback, reward, footer, modal, and chart surfaces consistently.
- Teacher and Admin components use `--shell-*` roles, and an automated source guard rejects colour literals outside the root token definitions.
- Runtime CPAT symbols, cue rings, pointer trails, ripples, heatmaps, and charts resolve the active theme at draw time and redraw when the theme changes.
- Correct and incorrect choices include check/cross cues, while current, selected, complete, warning, and focus states retain text, shape, border, or position cues in addition to colour.
- Reward-disabled/manual-advance feedback remains readable and exposes `Next` and `Repeat`; feedback no longer washes content with an opaque colour layer.
- Admin navigation now reveals focused destinations and defers landing until layout and stored history have settled.
- A 390-pixel mobile learner viewport keeps Help, Break, and Stop inside the visible area.

## Validation Record

- `77` Playwright tests passed locally: `56` stable/archive regressions and `21` alpha-specific checks.
- The alpha suite checks theme completeness, contrast, component token use, runtime-drawn colours, workspace navigation, reward and reward-disabled flows, tablet layout, and mobile containment.
- `scripts/capture-v170-visual-audit.js` produced `17` synthetic-data captures for teacher, Admin, active learner, reward, reward-disabled feedback, break, tablet, mobile, and every theme.
- Desktop Chromium visual review found the captured states coherent and fully visible at the tested viewports.
- `index.html` and the V1.6.0 versioned files remain outside the alpha implementation changes.

Automated results establish technical consistency, not learner suitability. Real staff and learner preference checks, physical Windows touchscreen, iPad Safari, Android Chrome, Kindle Silk, keyboard, and assistive-technology testing remain open.

## Acceptance Criteria

- every theme supplies every required semantic role
- no learner component requires a theme-specific selector patch
- no JavaScript interaction effect uses an unthemed UI colour
- all key text and non-text contrast pairs pass automated thresholds
- welcome, active task, prompt support, correct, incorrect, wait/no-go, reward, break, completion, and admin states are visually coherent
- every state remains understandable in grayscale and without relying on hue alone
- theme switching persists and updates charts/effects without reload
- stable V1.6.0 and `index.html` remain unchanged
- the complete browser suite and branch CI pass
- real staff and learner visual-preference checks remain a promotion gate

## Evidence Boundary

WCAG provides accessibility requirements for contrast and interaction visibility. It does not identify a universally beneficial colour palette for SEND learners. ChoiceTrain's named themes are configurable presentation options that must be validated during school trials.
