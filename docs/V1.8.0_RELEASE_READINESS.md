# V1.8.0 Release Readiness

## Purpose

This document separates ChoiceTrain's automated engineering checks from the human, school, governance, and research decisions required before V1.8 can replace the stable V1.7 GitHub Pages application.

V1.8 remains an isolated experimental candidate. Passing this checklist does not publish it, prove effectiveness, establish diagnostic validity, or approve a study protocol.

The machine-readable [promotion evidence record](V1.8.0_PROMOTION_EVIDENCE.json) is the current source of truth for external gates. It remains fully pending and non-authorising. The [evidence guide](V1.8.0_PROMOTION_EVIDENCE.md) explains how to record references without committing pupil or protected study data.

The separate pupil-data-free [implementation coverage manifest](V1.8.0_IMPLEMENTATION_COVERAGE.json) traces 16 internal requirements to exact repository evidence. It contains no commit-freeze or approval fields and delegates all 13 external gates to the promotion evidence record.

## Automated candidate gate

Run:

```bash
npm run check:candidate:v180
```

The dependency-free gate verifies that:

- `index.html` remains byte-identical to the protected `choice_train_V1.7.0.html` release and retains its reviewed SHA-256 hash
- the V1.8 HTML, JavaScript, and CSS candidate files exist and reference one another correctly
- candidate build metadata remains `1.8.0-alpha`, experimental, and explicitly unpublished
- trial schema 8, skill graph 1.4.0, generator 1.7.0, Research workspace export 2.3.0, delivery-context contract 1.0.0, photo schema 4/local migration 7, category-skill state 1.0.0, human-observation context 1.0.0, recommendation contract 1.5.0, retention-planning contract 1.0.0, privacy-minimised model dataset contract 1.3.0, trial-recording completeness schema 1.0.0, and Device readiness report 1.0.0 remain aligned
- the five active machine-readable JSON Schema contracts exist and parse as JSON Schema 2020-12 objects
- all 16 internal objective requirements retain implementation and automated evidence anchors, with limitations, while all 13 external gates remain exclusively controlled by the promotion record
- the static candidate runtime has no implemented browser network transport
- branch and Pages workflows run release, promotion-guard, schema, implementation-coverage, candidate, and browser checks
- branch and Pages workflows run a separate Android-like Chromium, iPad-like WebKit, and Kindle Silk-shaped compatibility smoke matrix
- the V1.8 plan retains explicit promotion, governance, and EEG hardware boundaries

The gate runs in branch CI and in the Pages workflow before deployment. It deliberately fails if the protected stable entry changes during V1.8 candidate development.

After committing the exact candidate and confirming a clean tracked worktree, generate the reviewer hand-off:

```bash
npm run build:review-pack:v180
```

The ignored JSON and Markdown files are written below `test-results/v180-review-pack/`. They identify the engineering snapshot and pending gate statuses but contain no pupil/session data, reviewer details, evidence references, candidate-freeze decision, or promotion approval. Store any protected review evidence separately under the school's approved process.

Review the candidate in desktop and tablet-sized Chromium views. The compatibility suite also exercises Android-like Chromium, iPad-like WebKit, and a Kindle Silk-shaped Chromium context. These automated profiles are useful regression evidence, but they do not reproduce every browser, hardware, accessibility, speech, performance, or touch characteristic and do not replace testing on the school's physical devices or with the intended access methods.

The isolated browser suite checks the optional pacing sequence as question prompt, blank pause, then answer choices, including event and EEG-marker order in the full export. It checks learner Q&A containment at representative 390 x 844 phone, 600 x 960 Kindle-sized, and 1366 x 768 laptop viewports; six-choice 320 x 568 portrait, 568 x 320 short landscape, and 844 x 390 compact landscape routes at 130% text; notch-safe viewport configuration; live visual-height and portrait-to-landscape relayout without changing the prompt, correct target, or question number; 320 x 568 enlarged-text Teacher/Admin and Research routes; and a 360 x 640 mobile photo editor. Active learner relayout changes presentation only and does not restart the response timer or emit stimulus/research markers. See the [adaptive layout contract](V1.8.0_ADAPTIVE_LAYOUT_CONTRACT.md). These Chromium dimensions are regression checks, not substitutes for physical Kindle Silk, iPad Safari, Android Chrome, Windows touchscreen, browser-zoom, virtual-keyboard, or assistive-access review.

The Admin System route can also refresh and download Device readiness report `1.0.0`. The browser test validates its closed schema, local-only and pupil-data-free declarations, observed viewport, current containment, 44-pixel Admin targets, filename, and exclusion of a synthetic pupil name and alias. Compatibility routes verify that the report is reachable in each emulated profile. The report is supporting evidence only; staff must still perform and record every applicable physical-device and assistive-access check.

The generator suite also creates two teacher-defined categories with six local personalised images, runs and replays a fixed-seed category lesson, and checks balanced target exposure, one valid answer, personalised source metadata, Research category visibility, and exclusion of image bytes from the export. This proves the tested local generator path, not the appropriateness, equivalence, or educational effect of practitioner-created content.

The separate compatibility smoke suite runs two routes in each emulated browser/device profile: question-to-answer pacing, four-choice containment, learner completion, runtime-error checking, and the local-only request boundary; then Teacher/Admin navigation at 130% text with horizontal containment and 44-pixel Admin navigation targets. Use the [external validation protocol](V1.8.0_EXTERNAL_VALIDATION_PROTOCOL.md) to collect the required staff, safeguarding, governance, physical-device, assistive-access, and EEG timing evidence without committing pupil data.

The V1.8 browser suite also constructs two sessions, downloads their raw full exports, independently recomputes final-attempt session-performance and per-skill count fields in the test process, and compares them with a separately downloaded current-learner Research summary. This is engineering evidence for reproducible core longitudinal aggregation; it is not validation of the educational interpretation or statistical analysis plan.

The suite also seeds the real browser stores with legacy settings and pupil keys, an older photo record and migration marker, and an existing session. It verifies that migration retains the legacy source records, creates the normalized learner and photo fields, preserves history, and produces an identical storage snapshot on a second startup. This is engineering evidence for non-destructive, idempotent migration; it does not replace backup, recovery, retention, or school-device testing.

The pseudonymised-export test also injects free text, an exact timestamp, and a source-session identifier into a stored EEG diagnostic object before download. The export must recompute diagnostics through the machine-readable allowlist and exclude all injected fields. This tests one minimisation boundary; it does not make the dataset anonymous or approve its use.

The teacher-review browser flow records an approved adjustment followed by a deferred revision. It verifies that the revision link persists across reload, that populated override controls cannot change session settings when deferred, that confirmed human observations remain attached to the review, and that the exported deferred record has `final_plan: null`. A separate regression confirms that visible 3/5 placeholders remain null and absent from Research charts until explicitly confirmed. The model-dataset contract limits decision codes to approve, adjust, decline, defer, or a null legacy value.

A separate browser flow explicitly stages an approved task and level, starts the unchanged setup, and verifies the recommendation/review IDs in the lesson, session, and trial records plus the linked-session count in Research. The privacy-export regression injects recommendation/review IDs, reviewer text, and an exact application time, then verifies that only the schema-locked application summary and aggregate use count remain.

The configurable-retention browser flow saves and reloads a 14-day interval, makes a recorded skill due after 15 days, verifies the deterministic delayed-check recommendation, records a later three-opportunity follow-up, and checks the due/observed cards, chart, table, full session export, and Research scope summary. It also confirms that the scope summary keeps day-level planned dates without exact wall-clock fields. This is engineering evidence for consistent scheduling and export behavior, not validation of the interval or a retention effect.

The category-skill browser flow completes two four-question sessions in one controlled category, then verifies the versioned state, repeated-sample status, accuracy matrix, full table, local future-tutor summary, day-level Research export, and all-learner suppression of recent trajectories. This is aggregation and interface evidence only; it does not validate the status thresholds, teaching recommendation, mastery, generalisation, or neural interpretation.

That flow now also expands the pupil's saved category selection, approves the deterministic category focus, stages it for one session, and verifies that the saved selection is unchanged while the frozen session content, lesson constraints, trial, review table, linked-session card, full export, and Research 2.2 summary all record the reviewed category. A separate Level 5 regression creates local teacher-declared discrimination sets, proves deterministic pair replay and generator integrity, visualises the controlled contrast basis, and verifies that neither the set name nor session-scoped audit token appears in model-development data. The wider model-export regression injects a teacher-created category label, free-text transfer observation, source-session ID, and exact observation date, then verifies that contract 1.3.0 emits only generic category provenance and the closed controlled observation subset. These are implementation and minimisation checks, not evidence that the selected category or discrimination set is pedagogically optimal or visually equivalent.

## Required human and external gates

The following cannot be approved by a repository script:

- product-owner approval to promote V1.8
- teacher and TA usability review using representative classroom workflows
- learner observation with appropriate safeguarding and assent or other authority processes
- school information-governance, privacy, retention, and access-control review
- legal and research-ethics approval for the intended study and data uses
- physical Windows touchscreen, iPad Safari, Android Chrome, Kindle Silk, keyboard, switch, AAC, and other relevant access testing
- EEG acquisition-system integration, separately implemented LSL or hardware triggers, and measured end-to-end timing latency
- protocol preregistration, condition allocation, blinding, artifact procedures, sample-size decisions, and statistical analysis planning

Any issue found at these gates should return the candidate to the feature branch rather than being worked around during promotion.

After the candidate is frozen and every external review has evidence, `npm run check:promotion:v180` must pass against that exact full commit SHA. The command fails on pending or failed gates, missing reviewer/date/reference fields, stale commits, unrecorded authorisation, and limitation-qualified approvals without explicit limitations. CI tests the guard itself but cannot supply or approve the external evidence.

## Promotion procedure

Promotion requires explicit approval. After approval:

1. Freeze the reviewed feature commit and confirm a clean worktree.
2. Run every engineering command above against that exact commit.
3. Record the external review references and accepted limitations in `V1.8.0_PROMOTION_EVIDENCE.json`, without pupil data.
4. Run `npm run check:promotion:v180` and retain its result with the release evidence.
5. Create reviewed stable V1.8 versioned files; do not overwrite older versioned releases.
6. Stamp the stable runtime with the approved version, channel, date, branch, and commit.
7. Update `index.html` only after the stable versioned files pass the complete suite.
8. Commit and push to `main`, then verify both the Pages workflow and the public URL.
9. Record the promoted commit, test totals, deployment run, and known limitations in `CHANGELOG.md`.

Until those steps are explicitly approved and completed, stable V1.7 remains the public source of truth.
