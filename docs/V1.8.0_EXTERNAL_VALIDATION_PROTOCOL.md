# V1.8.0 External Validation Protocol

**Status:** required before promotion

**Candidate:** `V1.8.0-alpha`

**Data rule:** keep pupil information, photographs, session exports, consent or authority records, safeguarding notes, and EEG recordings out of this repository. Commit only non-identifying evidence references and accepted limitations to `V1.8.0_PROMOTION_EVIDENCE.json`.

## Purpose

This protocol turns the V1.8 human and physical-device promotion gates into repeatable review activities. It complements automated engineering checks; it does not establish educational efficacy, clinical validity, legal authority, safeguarding approval, or hardware-synchronised EEG timing.

Run the protocol against one frozen 40-character candidate commit. If code changes after a finding, create a new candidate commit and repeat every affected review before authorising promotion.

## Before Testing

1. Freeze the candidate commit and record its full SHA in the approved evidence system.
2. Confirm the worktree is clean and the branch CI run for that SHA is successful.
3. Run the release, promotion-guard, schema, candidate, complete browser, and compatibility commands listed in `V1.8.0_RELEASE_READINESS.md`.
4. Use synthetic pupil profiles until the school has approved the intended data flow and learner participation process.
5. Assign a non-identifying evidence reference to each review. Do not use a pupil name or alias as an evidence ID.
6. Record the device, operating-system version, browser version, input method, orientation, accessibility settings, candidate SHA, reviewer role, date, outcome, limitations, findings, and retest reference.

## Staff Usability Review

Include teachers or TAs with different levels of ChoiceTrain familiarity and the school's SEND or accessibility lead. A developer may observe but should not guide participants unless the task has already failed.

### Daily classroom route

1. Open the candidate and identify that it is an experimental build.
2. Select or create a synthetic pupil profile.
3. Confirm the level, task, question count, timing, prompt, speech, reward, and blank-interval settings.
4. Select categories and confirm the session-readiness message.
5. Start learner mode and complete a short session.
6. Request Help and Break, then continue.
7. Return to the teacher workspace using the deliberate press-and-hold control.
8. Locate the session result, Research view, and ordinary session export.
9. Explain what Reset clears and what pupil history remains stored.

### Research and recommendation route

1. Change Research scope and identify the learner/session count represented.
2. Locate Attention Training families, omissions/commissions, timing, touch, support, retention, transfer, fidelity, artifacts, marker quality, and recommendation history.
3. Confirm that charts have readable table or text equivalents.
4. Review a deterministic next-session proposal and record approve, adjust, decline, or defer.
5. Confirm that only an approved plan can be staged and that staging does not start a session automatically.
6. Confirm that descriptive practice states and recommendations are not presented as diagnosis, mastery, neural change, or proof of transfer.

Record completion, first-attempt completion, time, wrong turns, questions asked, accidental starts or exits, and confidence on a 1-5 scale. A task fails if developer intervention is needed.

Suggested acceptance criteria are:

- every participant completes the daily route without developer intervention
- at least 80% of staff tasks complete on the first attempt
- no blocker or unresolved high-severity issue remains
- staff can explain the local-storage and export boundary in plain language
- staff do not interpret the application as diagnostic or autonomously prescriptive

These are product-release criteria, not research outcomes.

## Learner Safeguarding Observation

Use the school's approved safeguarding, assent or other authority, regulation, and stopping procedures. Begin with the least intrusive sound, motion, reward, brightness, prompt, and duration settings and adapt to the learner rather than enforcing one configuration.

Observe whether the learner notices the prompt and target, can request help/break/stop, accidentally activates controls, experiences fatigue or sensory discomfort, and can use their intended access method. Stop or adapt immediately under the school's normal practice if distress, withdrawal, overload, pain, or safeguarding concern is observed.

Do not commit the observation record to GitHub. The repository promotion record should contain only the external review reference, reviewer role, date, outcome, and any non-identifying release limitation.

## Physical Device Matrix

Complete every applicable row on real hardware. Browser emulation and the automated WebKit/Chromium compatibility smoke suite are regression evidence only.

| Gate | Minimum physical check | Required evidence |
|---|---|---|
| Windows touchscreen | Supported Windows laptop/tablet, current intended browser, touch and keyboard | Device/browser versions, input methods, orientations, result and findings |
| iPad Safari | Intended iPad generation and current supported Safari/iPadOS | Device/iPadOS/Safari versions, portrait/landscape result and findings |
| Android Chrome | Representative intended Android phone/tablet and current Chrome | Device/Android/Chrome versions, portrait/landscape result and findings |
| Kindle Silk | Intended Kindle model and current Silk/Fire OS | Device/Fire OS/Silk versions, portrait/landscape result and findings |

On each device:

1. Load the candidate from the intended deployment route.
2. Confirm Teacher and Admin/Research navigation is operable.
3. Start learner mode with four answer options.
4. Verify prompt, optional question-to-answer blank interval, answers, progress, feedback, Help, Break, and Stop remain visible and operable.
5. Verify no question or answer is clipped or placed outside the usable viewport in portrait and landscape where supported.
6. Rotate during an unanswered question and confirm that the same prompt and answers remain available without a duplicate question, skipped trial, or restarted session.
7. Repeat a multi-choice task with the largest intended answer count and the pupil's intended text size or browser zoom.
8. Complete touch-screen, touch-object, moving-target, category, and one Attention Training task.
9. Return with the deliberate hold control and confirm an ordinary tap does not exit learner mode.
10. Toggle speech; confirm supported speech is understandable and unsupported speech fails without blocking the activity.
11. Reload and confirm local pupil/settings persistence expected for that browser mode.
12. Export a synthetic session and confirm the filename and required metadata.

A physical-device gate is not passed while a blocker, data-loss issue, broken target, learner trap, or severe layout/access problem remains. Record browser limitations as `passed-with-limitations` only when the responsible reviewer explicitly accepts them.

## Assistive Access Review

Test the access methods the school intends to support, such as keyboard, switch input that emits keyboard or pointer events, AAC-supported prompting, zoom, and screen-reader review of teacher/research controls. Record the actual hardware and software rather than inferring support from browser emulation.

Confirm visible focus, logical order, operable controls, understandable labels, non-colour state cues, chart alternatives, and a safe learner-to-teacher return. If an access method is out of scope, state that limitation explicitly rather than marking it passed.

## Information Governance and Legal/Ethics Review

The responsible school and research roles should review:

- local browser storage, shared-device access, backups, retention, deletion, and device disposal
- pupil profiles, photographs, context notes, teacher observations, exports, and pseudonymous participant codes
- who may run sessions, see dashboards, export data, and move files off the device
- lawful basis or consent/authority processes for classroom, research, EEG linkage, and model-development purposes
- safeguarding, DPIA, research-ethics, withdrawal, incident, and data-subject-rights processes
- the deny-by-default model-development export and the fact that pseudonymised data remains personal data
- the absence of cloud LLM calls and the prohibition on treating local recommendations as autonomous decisions

ChoiceTrain records only a local declaration and non-secret reference. It does not store or verify the underlying approval evidence.

## EEG Hardware Timing Review

Do not pass this gate using browser marker exports alone. The study team must separately implement and validate the chosen LSL or device-specific trigger bridge against the intended acquisition system.

The external timing record should identify:

- acquisition system, display/audio hardware, browser/device, bridge version, sampling rate, and marker transport
- marker mapping for cue, prompt, blank interval, stimulus, target/no-go, response, omission, commission, feedback, prompt support, break, artifact, and session completion
- measurement method, reference sensor or photodiode/audio-loop method, trial count, clock alignment, and warm-up procedure
- latency distribution, jitter, dropped/duplicated/out-of-order markers, clock drift, and condition-specific limitations
- pre-specified acceptance thresholds from the approved protocol

ChoiceTrain deliberately does not provide a universal latency threshold because the acceptable bound depends on the registered ERP design, acquisition chain, and analysis plan. Record the measured outcome and accepted limitations in the approved external evidence system.

## Finding and Retest Rules

- **Blocker:** data loss/disclosure, learner trap, broken target/rule, invalid research event, unsafe access failure, or stable-release regression.
- **High:** cannot start, return, save, review, or export; severe physical-device layout or accessibility failure.
- **Medium:** confusing workflow, inconsistent wording/state, or non-critical sound, motion, timing, or layout defect.
- **Low:** polish or optional enhancement.

Fix blocker and high findings on the feature branch. Link each fix to a new commit and retest every affected gate. Do not carry a stale approval forward to changed code without reviewer confirmation.
